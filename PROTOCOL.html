Broker Approval Protocol

How you approve, from your phone, each time the broker fills a password, one-time code or card for an agent. A relay you host yourself carries the messages but can't read them and can't approve anything. Your answer (one tap, a PIN, or an authenticator code) is checked on your own machine.

What changed from v0.1

  • No passkey. Approval is one of three methods: tap, PIN, or authenticator code. The broker checks the answer.
  • Noise instead of HPKE + signatures. One standard handshake does encryption, authentication and binding of your answer to the request, with forward secrecy for everything you send.
  • Keyless relay, for real. The broker sends push notifications itself, so the relay only stores and forwards ciphertext. Anyone can deploy one.
  • Simpler pairing. A secret in the QR code authenticates the handshake, which replaces the commitment and 6-digit match.

Who holds what

Four parties, plus the phone vendor's push service. The design rests on where the keys are. The relay and the agent hold none.

One approval, step by step

Example: the agent reaches a bank's SMS-code page. Each approval is one Noise KK handshake of two messages. The request goes out in the first; your answer (and the SMS code) comes back in the second, encrypted under keys that depend on that exact request.

The three approval methods

The broker chooses the method and writes it into the request (approve_with). Which method applies to which request is not decided yet. For now it's a setting per fill, and a risk policy can choose it later. The phone can't downgrade: the broker checks the answer against the method it asked for.

Pairing, once

  1. On your machine, run broker pair --relay https://your-relay. It shows a QR code holding the relay URL, a random mailbox ID, the broker's public key B, and a random 256-bit key K. K sits after the #, which browsers never send to a server.
  2. Scan it with the phone camera and add the page to the Home Screen.
  3. The web app creates P, a non-extractable X25519 key kept in the browser. It runs a Noise XXpsk3 handshake with the broker through the relay, using K as the pre-shared key. Its last message carries the device name and the push subscription.
  4. Your machine asks "Pair iPhone (key ab12 cd34)? y". On yes, the broker pins P and the phone pins B.

Why it resists a man in the middle: the handshake only completes for someone who knows K. K travels optically from your screen to the camera and never reaches the relay, so a relay that substitutes its own keys fails the handshake. This also removes v0.1's 6-digit match and the commitment it needed against code-guessing.

Assumption: only you see the QR code: on the machine's own screen, or through your encrypted remote-desktop session. It's valid for 2 minutes and works once.

Lost phone: run broker revoke, then pair the new phone. A stolen phone still needs your PIN or authenticator code for requests that ask for one.

Message formats

suite     Noise_XXpsk3_25519_AESGCM_SHA256      pairing, once
          Noise_KK_25519_AESGCM_SHA256          each approval (both static keys pinned)
          X25519 · AES-256-GCM · SHA-256: native in WebCrypto and Python; noble fallback

R  = { v:2, id:uuid, site:"bank.example.com", cert_sha256:"9f2c41d0…", frame:"bank.example.com",
       kind:"otp"|"password"|"card"|"cvc", item:"Bank SMS code", amount:null,
       warnings:["first time on this site"], approve_with:"validate"|"pin"|"otp",
       needs_secret:"one-time code"|null, created:t, expires:t+120s }

msg 1  broker → phone   KK  -> e, es, ss   payload = JCS(R)            # RFC 8785 canonical JSON
msg 2  phone → broker   KK  <- e, ee, se   payload = JCS({ id, decision:"approve"|"deny",
                                                       answer: null | pin | totp,
                                                       secret: null | "…" })
relay envelope          { mailbox: 16B random, n: 1|2, noise: bytes }   # all the relay sees

pairing  XXpsk3 (phone starts):  -> e   <- e, ee, s, es   -> s, se, psk     psk = K (QR #fragment)
         msg 3 payload = { device_name, push_subscription }
push     RFC 8291 Web Push, payload "approval waiting", VAPID (RFC 8292) key on the broker,
         sent by the broker straight to Apple/Google: the relay is not involved
outer    TLS 1.3 to the relay (defence in depth only)

Why the answer can't be moved to another request: Noise derives every message key from a running hash of the handshake, request R included. Message 2 only decrypts for the broker's state for this one request. That is the job the passkey challenge did in v0.1.

Why a secret can't be swapped in: message 2 is authenticated with your phone's key (se), so the relay can't insert its own password or card.

Forward secrecy: message 2 (your answer, PIN or code, and any secret) is encrypted with fresh keys on both sides (ee), so a key stolen later can't decrypt it. Message 1 has weaker forward secrecy, a known property of Noise KK's first message, but it carries no secrets.

Replay: the broker keeps one handshake state per request and drops it after the answer or 2 minutes, so a replayed message 2 matches nothing. The phone ignores expired or already-seen requests.

Run your own

  1. Deploy the relay: a small Docker image with one-click templates (Railway first, then Fly and Render), or docker run. No secrets to configure, no database: mailboxes live in memory for 2 minutes.
  2. Pair: broker pair --relay https://your-relay, scan the QR code, add it to the Home Screen, press y.
  3. Connect your agent: it calls the broker over MCP. It never talks to the relay or the phone.

Today the broker runs on Linux (X11) with Chrome. macOS and other browsers fit behind the same interfaces later. The protocol doesn't depend on them.

Hard floors, never filled even with approval

Changing passwords, moving money between accounts, adding payees, and pressing Pay or Submit. These follow OpenAI Dots and Claude Duet, which keep the same actions for the human. The broker refuses them, and pressing Pay stays a separate yes from you.
